# 05 · 路线图与待确认决策

> 本阶段（M0）只交付设计，不写代码。本文给出建议的迭代顺序、每个里程碑的完成标准，以及需要你拍板的 D1–D12。确认后从 M1 开始。

## 1. 里程碑

> 工期是「一名开发者 + AI 辅助」的粗略估算，用于判断先后顺序，不作为承诺；确认范围后会在开工前再细化。

| 阶段 | 目标 | 主要交付 | 粗略工期 |
| --- | --- | --- | --- |
| **M0 设计确认**（当前） | 架构、需求、场景机制达成一致 | 本文档集 + PR 评审 + 决策结论 | 现在 |
| **M1 能聊起来** | 打通「配置模型 → 流式对话 → 落库」 | monorepo、CI、SQLite 迁移、provider CRUD、密钥加密、OpenAI 兼容适配器、SSE 生成、停止 / 重写、Ant Design 页面骨架、分段输入、AI 推荐下一条 | 1.5–2 周 |
| **M2 像酒馆** | 角色、人设、会话、分支 | 角色 CRUD、V2 JSON/PNG 导入、头像、开场白、人设、会话管理、分支切换、简单 / 高级模式骨架 | 1.5 周 |
| **M3 场景核心** ✅ 核心 | 场景插入 + 上下文可解释 | 提示词引擎、宏、token 预算、三种意图入口、时间线场景卡片、场景面板 / 编辑器、上下文预览、快照测试；模板 / 状态栏待补 | 2–2.5 周 |
| **M4 可用与可迁移** | 能长期用、能带走 | 导出 / 导入、首次引导、错误处理、性能打磨、E2E、文档 | 1–1.5 周 |
| **M5 P1 增强** | 补齐酒馆常用能力 | 世界书、预设高级编辑、Anthropic / Gemini、场景模板、状态栏、长对话摘要、Ollama 自动发现、Docker | 按需排期 |

### 各阶段完成标准（Exit Criteria）

**M1**

- 能添加一个 DeepSeek / OpenAI 兼容 provider，测试连接成功，并发起流式对话。
- 刷新页面后消息仍在；停止生成保留部分内容；重写生成兄弟消息。
- 密钥只存在服务端，API 响应与日志不出现明文。
- 适配器 fixture 测试、API 集成测试通过。

**M2**

- 能导入一张 SillyTavern V2 PNG 角色卡，正确带出头像、开场白、示例对话。
- 能选择开场白新建会话、切换人设、在分支间切换且上下文正确。

**M3**

- [04 场景插入设计](04-scene-injection.md) 中的 4 个典型用法全部可用。
- 上下文预览与实际发出的请求**逐段一致**（由快照测试保证）。
- `depth` 边界、锚点失效、裁剪、一次性消费均有测试覆盖。

**M4**

- 全流程 E2E：配置 mock provider → 导入角色卡 → 聊天 → 插入场景 → 预览 → 重写 → 导出 → 导入还原。
- 1 万条消息会话滚动流畅；上下文装配 < 50ms。
- 首次使用 3 分钟内能发出第一条消息。

## 2. 待确认决策

请在 PR 评论或飞书里按 `D1=A，D2=A，…` 回复；未特别指定的按**推荐**执行。每项都可以选推荐之外的方案，我会据此调整设计。

### D1 部署形态

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 本地 Web：浏览器访问本机 Node 服务，数据在本地 SQLite |
| B | Docker 自托管（本质上仍是 A，多一层打包） |
| C | 桌面应用（Tauri / Electron 外壳） |
| D | 云端多用户服务 |

**推荐理由**：最贴合「自己的模型、自己的数据」，开发成本最低，后续可平滑加 Docker / 桌面壳。选 D 会显著增加账号、隔离、计费与合规成本，不建议在 MVP 做。

### D2 技术栈

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | React 18 + Vite + Fastify + SQLite（`node:sqlite`，可迁移 Drizzle）+ **Ant Design 5 / Ant Design X**，pnpm monorepo |
| B | Next.js 全栈（一体化，SSR 对本场景收益低） |
| C | 其他（请说明偏好，如 Vue / Svelte / Python 后端） |

**推荐理由**：前后端边界清晰、流式代理直接、便于未来桌面化；TypeScript 全栈共享类型。组件用 Ant Design 5（表单 / 弹窗 / 抽屉 / 主题）与 Ant Design X（AI 对话组件），减少自研；若个别 AI 组件覆盖不足，用 assistant-ui 补位。若你更熟悉 Next.js，B 也能做，只是要注意流式路由与本地打包。

### D3 首版模型适配范围

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 只做 OpenAI 兼容协议（覆盖 DeepSeek、OpenRouter、中转站、Ollama、LM Studio、自建） |
| B | A + Anthropic 原生 |
| C | A + Anthropic + Gemini 原生 |
| D | 首版全部 |

**推荐理由**：OpenAI 兼容已覆盖绝大多数用户与本地模型；原生协议可以 P1 加，适配器接口已预留。若你主要用 Claude / Gemini，可提到 MVP。

### D4 场景插入形态

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 三种位置都做：系统常驻 + 深度 + 时间线锚定；两种时长：持续 + 仅下一轮 |
| B | 只做深度插入（接近酒馆作者注记） |
| C | 只做时间线锚定（像在对话里插旁白） |

**推荐理由**：三种位置解决的是不同问题——长期设定、单轮导演、剧情事件；只做一种会让用户回到「改角色卡 / 重开会话」的老路。实现上共用同一套场景模型，增量成本可控。

### D5 场景默认身份

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 默认 `system`（舞台说明），高级里可改 user / assistant |
| B | 默认 `user`（旁白口吻） |
| C | 每次插入时强制选择 |

**推荐理由**：system 最符合「导演说明」语义，也最不容易被模型当成用户台词回应；不支持历史中 system 的模型由适配器自动降级并提示。

### D6 世界书优先级

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | P1：MVP 先把场景与角色做扎实，世界书紧随其后 |
| B | P0：酒馆用户的核心预期，首版必须有 |
| C | 不做世界书，只靠角色卡与场景 |

**推荐理由**：世界书是酒馆重度用户的刚需，但实现涉及关键词扫描、位置、预算分配与导入兼容，容易拖慢核心场景体验。数据模型已预留，P1 加不改表结构。若你的使用方式高度依赖世界书，可选 B。

### D7 群聊 / 多角色同场

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | P2 |
| B | P1 |
| C | 不做 |

**推荐理由**：群聊涉及发言顺序、多角色提示词、上下文归属，是独立的大模块；先保证单角色体验。

### D8 多用户 / 云端

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 单用户本地；预留局域网访问令牌 |
| B | 多用户 + 登录 + 数据隔离 |

**推荐理由**：当前需求是个人创作工具；多用户会改变数据模型、密钥管理与部署形态，不宜在 MVP 引入。

### D9 角色卡兼容版本

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | V2（JSON / PNG）；V3 字段尽量容错，P1 完整支持 |
| B | 首版就完整支持 V3 |
| C | 只支持自建格式 |

**推荐理由**：V2 是当前生态事实标准；V3 仍兼容 V2 字段，先导入不报错、保留原始字段，P1 再补齐。

### D10 内容安全策略

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | 本地单用户自用：默认不做服务端内容过滤；公开部署时提供年龄提示与可开关的过滤 |
| B | 始终启用内置内容过滤 |
| C | 暂不讨论，按平台要求再定 |

**推荐理由**：这是个人本地工具，服务端过滤既无法覆盖用户自接的模型，也会破坏创作自由度；但一旦对公网开放，需要明确年龄门槛与开关。选 B 会影响部分角色扮演场景的可用性。

### D11 场景状态栏

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | P1：时间 / 地点 / 在场人物结构化展示，一键编译为系统常驻场景 |
| B | P0：首版就要有 |
| C | 不做，直接编辑场景文本 |

**推荐理由**：状态栏提升「持续场景」的易用性，但本质是场景的 UI 糖；P0 先把三种位置与预览做稳。

### D12 自动生成场景

| 选项 | 说明 |
| --- | --- |
| **A（推荐）** | P2 再议：让模型根据剧情建议下一场景，需额外调用与成本控制 |
| B | P1 |
| C | 不做 |

**推荐理由**：自动建议会引入额外模型调用、延迟与「AI 改戏」的不可控感；先把手动插入做到极致。

### 决策汇总

| 编号 | 决策 | 推荐 |
| --- | --- | --- |
| D1 | 部署形态 | A 本地 Web |
| D2 | 技术栈 | A React + Vite + Fastify + SQLite + Ant Design |
| D3 | 首版模型适配 | A OpenAI 兼容 |
| D4 | 场景插入形态 | A 三种位置 × 两种时长 |
| D5 | 场景默认身份 | A system |
| D6 | 世界书 | A P1 |
| D7 | 群聊 | A P2 |
| D8 | 多用户 | A 单用户 |
| D9 | 角色卡版本 | A V2（V3 容错） |
| D10 | 内容安全 | A 本地默认不过滤 |
| D11 | 场景状态栏 | A P1 |
| D12 | 自动生成场景 | A P2 |

### 已采纳的用户反馈（2026-11-10）

以下两项已按反馈写入 P0，不再作为开放决策：

- **新手优先的交互**：默认简单模式、内置推荐参数、三种场景意图；深度 / 身份 / 排序 / token 细节收进高级选项。
- **成熟组件**：Ant Design 5 + Ant Design X（必要时 assistant-ui）等现成 React 组件，不自研基础控件。

## 3. 风险清单

### 3.1 产品风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 场景遵循率不稳定 | 模型可能忽略或过度发挥导演指令 | 标准包装模板、默认靠近末尾、身份可选、预览可见；在文档中说明这受模型能力影响 |
| 功能范围膨胀 | 酒馆功能很多，容易什么都想做 | P0 严格锁定本文范围；世界书 / 群聊 / 多模态后置 |
| 组件库限制表达 | 成熟组件不一定完全贴合场景卡片 / 上下文预览 | 领域组件用 antd 原语组合；不为了视觉自研基础控件 |
| 与酒馆体验差距 | 用户会拿细节对比 | 优先保证角色卡导入、分支、深度语义、导出四个高频点 |
| 内容边界争议 | 公开部署时的合规风险 | 默认本地单用户；公开部署前单独评估（D10） |

### 3.2 技术风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 模型协议差异 | system 位置、role 交替、usage、reasoning 字段不统一 | 适配器能力标记 + 归一化 + fixture 测试 + 预览显示实际角色 |
| token 估算偏差 | 中文 / 不同 tokenizer 差异大 | 保守余量、真实 usage 校准、允许手改上下文窗口 |
| 流式稳定性 | 断流、重复、取消后脏数据 | 状态机、增量落盘、幂等结束、取消测试 |
| 长对话性能 | 消息多导致卡顿 | 虚拟列表、分页、只装配窗口、索引 |
| 密钥安全 | 本地文件被读 | AES-GCM + 0600 主密钥 + 响应掩码 + 日志脱敏 |
| SQLite 并发 | 多请求写冲突 | 单进程串行写、WAL、busy_timeout |

## 4. 明确不做（MVP）

- 图像生成、TTS / 语音输入、语音通话。
- 多角色群聊 / 多人同房。
- 账号体系、云同步、社区分享、角色卡市场。
- 模型训练 / 微调、内置额度或代理。
- 联网搜索、代码执行、通用 Agent 工具。
- 移动端原生 App。

## 5. 确认与下一步

1. 在 PR 评论或飞书里回复决策（或直接说「按推荐来」）。
2. 我根据结论更新本文档与相关设计（如有变更），冻结 M1 范围。
3. 创建 M1 开发任务：项目骨架、provider 接入、流式对话、消息落库。
4. 之后每个里程碑单独评审，场景核心（M3）完成后再做一次体验验收。

### M0 完成定义

- 架构、数据模型、API、场景机制四份设计可评审、无自相矛盾。
- D1–D12 有明确结论（或明确接受推荐）。
- M1 的范围、完成标准、风险已确认。
- 确认后无阻塞开发的开放问题。
